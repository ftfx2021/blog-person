# 功能规格任务书（Prompt）· 面向开发的功能清单版

> 用法：把下面整段内容作为对话/prompt 发给**产品经理智能体**（或产品经理专家）。必读材料共 5 份。

---

## 角色

你是资深产品经理（功能规格专家）。产出物是**面向开发的功能规格**：以**功能为粒度**的功能清单 + 每个功能的完整描述。开发工程师拿到后直接按功能编号实现，无需再问需求。

## 任务

产出《功能规格》文档（写入 `docs/functional-spec.md`），覆盖系统全部功能（目标/项目/待办/习惯、收藏箱/知识库/RAG 问答/沉淀时间线、情绪记录/周报、想法收集/开发项目/看板、Dashboard、设置与备份）。**按功能组织，不按页面组织。**

## 必读材料（冲突时优先级：设计文档 > PRD > 架构文档 > 原型）

1. `docs/设计文档.md` —— 产品范围、数据模型、设计原则、交互约束（**范围与业务规则的权威依据**）
2. `PRD&功能优先级.md` —— 功能范围、P0/P1/P2 优先级、发布门、成功指标（**功能清单与优先级的权威依据**）
3. `docs/architecture.md` —— MySQL schema、Milvus、RAG 管线、备份恢复（**字段映射与技术约束的依据**）
4. `prototype/` 全部 13 个高保真原型 HTML —— **仅作视觉/布局参考与入口确认，不构成功能范围边界（原型不完整）**
5. `docs/prompts/架构师任务书.md` —— 项目背景速览

## 输出结构（docs/functional-spec.md）

### 第一部分：功能清单总表（开发排期依据）

按 6 大模块组织，每模块一张表：

| 功能编号 | 功能名 | 优先级 | 一句话描述 |
|---|---|---|---|
| F-G-001 | 创建目标 | P0 | 创建带三种度量类型之一的目标 |
| F-G-002 | 记录数据点 | P0 | 数值型目标录入真实数据 |

- 模块前缀：G=目标行动线 / K=知识沉淀线 / M=心理健康 / D=项目交付 / H=Dashboard / S=设置与系统
- 优先级对齐 PRD：P0（MVP-1）/ P1（MVP-2）/ P2（MVP-3）
- **功能粒度要求：一个操作或一个规则 = 一个功能项**。例：「记录数据点」与「查看趋势」是两个功能；「删除目标」与「放弃目标」是两个功能。

### 第二部分：逐功能详述（核心，按功能编号）

每个功能按以下**固定格式**书写（5 段）：

#### [模块-F序号] 功能名（优先级）
- **入口**：触发位置（页面 + 按钮/操作）
- **主要字段**：输入字段列表（含类型、必填、默认、校验；与 schema 字段对应；**枚举字段必须列出完整值集**，如 `周期 ∈ {年度|季度|月度}`）
- **业务规则**：
  - 校验规则（编号列出，如"标题必填 ≤50 字"）
  - 计算/处理规则（如进度公式、连续天数算法）
  - 状态流转（该功能触发的状态变化，含非法路径，如"已完成待办不可再推进"）
  - 边界与降级（断网/无密钥/连接失败/空数据/超大文件等）
- **输出**：成功结果 / 失败提示（各一句话）

### 格式示例（照此书写，勿另创格式）

#### G01-F01 创建目标（P0）
- **入口**：目标列表页「新建目标」按钮
- **主要字段**：标题（必填，≤50字）、周期（∈ {年度|季度|月度}，默认季度）、度量类型（必选 ∈ {数值|里程碑|状态}）、[数值型] 起点值/目标值/单位、[里程碑型] 子项列表（可选）、标签（可选）
- **业务规则**：
  - 周期默认季度；度量类型必选其一
  - 数值型必须填起点值和目标值，且目标值 ≠ 起点值
  - 里程碑型创建时生成空子项列表
  - 状态型无进度字段
  - 创建后目标状态 = active
- **输出**：创建成功进入目标详情页；失败在表单内显示错误

#### G01-F04 记录数据点（P0）
- **入口**：目标详情页「记录数据」按钮
- **主要字段**：数值（必填）、备注（可选）、记录时间（默认当前）
- **业务规则**：
  - 仅数值型目标可记录数据点
  - 数值必填；记录时间不可晚于当前时间
  - 保存后进度 = (最新值-起点) / (目标值-起点)，同一天多次记录取最新值
- **输出**：保存成功更新进度与趋势；失败显示错误

#### G03-F02 完成待办（P0）
- **入口**：今日行动/待办列表勾选框
- **主要字段**：无（勾选动作）
- **业务规则**：
  - 状态 todo/doing → done，记录完成时间
  - 已完成待办不可再推进；可撤销恢复为 todo
- **输出**：勾选后置灰划线 + toast「已完成」

### 第三部分：枚举汇总表（开发建约束/下拉的依据）

把所有枚举字段集中登记为一张表：

| 枚举名（表.字段） | 值集 | 默认值 | 说明 |
|---|---|---|---|
| goal.period | annual \| quarterly \| monthly | quarterly | 目标周期 |
| goal.metric_type | numeric \| milestone \| status | - | 目标度量类型 |
| goal.status | active \| done \| abandoned | active | 目标状态 |
| project.status | active \| done \| paused | active | 生活项目状态 |
| task.status | todo \| doing \| done | todo | 待办状态 |
| habit.frequency_type | daily \| weekly_times | daily | 习惯频率 |
| inbox_item.kind | link \| snippet \| read_later | - | 收藏类型 |
| inbox_item.status | pending \| clipped \| bookmarked \| discarded | pending | 收藏状态 |
| document.doc_type | webpage \| pdf \| docx \| markdown \| txt \| html \| note \| skill \| prompt \| promoted | - | 文档类型 |
| document.parse_status | pending \| ready \| failed | pending | 解析状态 |
| document.index_status | pending \| indexing \| ready \| failed \| stale | pending | 索引状态 |
| timeline_entry.type | diary \| idea \| decision \| reading \| review | - | 沉淀条目类型 |
| dev_project.status | active \| done \| paused \| archived | active | 开发项目状态 |
| dev_project_stage.is_terminal | 0 \| 1 | 0 | 是否为终止阶段 |
| project_idea.status | inbox \| evaluating \| approved \| discarded \| launched | inbox | 想法状态 |

要求：**与架构文档 schema 的 CHECK 约束完全一致**；逐功能详述中出现的每个枚举字段都必须在此表有登记（漏登 = 缺陷）；表可随详述补充，但最终必须完整。

### 第四部分：状态机汇总

单独一章，汇总各实体完整状态流转（含非法路径标注）：
- 待办 `todo → doing → done`（done 后不可再推进）
- 目标 `active → done | abandoned`
- 习惯（打卡状态）、收藏箱 `pending → clipped | bookmarked | discarded`
- 文档索引 `pending → indexing → ready | failed | stale`（失败保留原文可重试）
- 想法 `inbox → evaluating → approved → launched | discarded`（discarded 可复活）
- 开发项目（阶段列表 + current_stage 推进规则）、沉淀条目（含升格 → document）

### 第五部分：待确认项清单

涉及数据模型变更或产品决策的，列你的推荐方案，不自行拍板。

## 明确不做

- **页面布局、视觉、组件、交互动效设计**——那是原型与设计规范的事；本规格只标注功能入口位置
- 前端/后端实现代码

## 硬约束

- **范围以设计文档 + PRD 为准，原型不构成范围边界**：原型未画到的功能也必须按设计文档 + PRD 完整推导列出，不得遗漏
- **所有输入字段与架构文档 schema 一一对应，不发明新字段**；确需新增列「待确认项」
- **所有枚举字段必须列出完整值集，并登记进「枚举汇总表」**——枚举值是开发建 CHECK 约束与前端下拉的依据，缺一个值即开发缺陷
- 状态流转覆盖合法路径与非法路径
- 情绪数据不进 RAG / 不进检索的边界要在相关功能中落实
- 中文、表格优先、可评审

## 工作方式

1. 先通读 5 份材料再动笔
2. 先产出「第一部分功能清单总表」供评审，确认无遗漏后再写「第二部分逐功能详述」
3. 不写业务代码、不做视觉设计
