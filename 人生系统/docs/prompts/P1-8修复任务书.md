## 五、实现要求

### 5.1 停止立即中断底层请求（F-1，核心）

**问题根因**：`openai-compatible.ts` 的 `request()` 每次创建独立 `AbortController` 只服务于超时，`chatStream` 不接收外部取消信号。`chatService.stop()` 只能等下一个 chunk 到达后 break，网络请求不会立即释放。

**改造**：

`src/main/infrastructure/llm/types.ts`——`ChatRequest` 增加可选 signal：

```ts
export interface ChatRequest {
  messages: ChatMessage[];
  model: string;
  temperature?: number;
  maxTokens?: number;
  stream?: boolean;
  // 外部取消信号：调用方（如停止按钮）abort 时立即中断底层 fetch，而非等下一个 chunk。
  signal?: AbortSignal;
}
```

`src/main/infrastructure/llm/openai-compatible.ts`：
- `request(body: unknown, signal?: AbortSignal)` 增加第二参数；在函数内把外部信号与超时信号**合并**：

```ts
private async request(body: unknown, externalSignal?: AbortSignal): Promise<Response> {
  let lastError: unknown;
  for (let attempt = 0; attempt < MAX_ATTEMPTS; attempt += 1) {
    // 超时与外部取消各自独立；同时触发时都以 abort 语义结束本轮请求。
    const controller = new AbortController();
    const timeout = setTimeout(() => controller.abort(), REQUEST_TIMEOUT_MS);
    // 外部信号（停止按钮）触发时同步 abort 内部请求，实现立即中断。
    const onExternalAbort = () => controller.abort();
    externalSignal?.addEventListener("abort", onExternalAbort, { once: true });
    try {
      ...fetch(..., { signal: controller.signal })...
    } finally {
      clearTimeout(timeout);
      externalSignal?.removeEventListener("abort", onExternalAbort);
    }
  }
}
```

- 重试语义保持不变：外部 abort 属于用户主动取消，**不应重试**——`onExternalAbort` 触发后本轮 fetch 抛 AbortError，捕获时若 `externalSignal?.aborted` 为 true 则**直接 throw**（不进入退避重试）
- `chatStream(request)` / `chat(request)` 内部调用 `this.request(this.buildBody(request, true), request.signal)`
- `chat()` 非流式路径同样传 `request.signal`

`src/main/modules/chat/service.ts`——`run` 中调用 provider 时传信号：

```ts
for await (const chunk of provider.chatStream({
  messages, model: config.model, temperature: 0.7, stream: true,
  signal: active.controller.signal,   // 停止按钮 → 立即中断 fetch
})) { ... }
```

### 5.6 首字探测 + 流式优化（F-6）

### 5.7 超时策略分层（F-7）

**问题**：`openai-compatible.ts` 当前 `REQUEST_TIMEOUT_MS = 30_000` 是**整个请求**的总超时——长思考模型（DeepSeek-R1 / OpenAI o 系）思考可超过 30s，会被误杀。

`src/main/infrastructure/llm/openai-compatible.ts`：
- 常量拆为三档，构造时可覆盖：
  - `CONNECT_TIMEOUT_MS = 10_000`：fetch 建立连接阶段
  - `FIRST_TOKEN_TIMEOUT_MS = 60_000`：请求发出到收到**第一个 SSE 事件**（含模型思考期）
  - `STREAM_IDLE_TIMEOUT_MS = 30_000`：流式过程中相邻两个事件的最大间隔
- 实现：`request()` 用 `CONNECT_TIMEOUT_MS` 覆盖连接期（fetch 完成前）；`chatStream` 里 `readSse` 循环中维护 idle 计时器（`setTimeout(STREAM_IDLE_TIMEOUT_MS)`，每个事件到达时重置，超时抛 `AI_TIMEOUT`）；首字超时 = 请求开始到第一个 `yield`，用 `FIRST_TOKEN_TIMEOUT_MS` 单独计时
- **错误码**：`src/shared/contracts/common.ts` 的 `errorCodeSchema` 末尾追加 `"AI_TIMEOUT"`；渲染层文案「AI 响应超时：模型思考或网络延迟过长，请重试」
- 超时错误**不重试**（F-10 的断流重试除外），与 `AI_UNAVAILABLE` 区分展示

> 注：超时阈值放宽（慢模型/深度思考误杀问题）与 Markdown 渲染库调整见独立任务书 `docs/prompts/AI助手补充修复任务书.md`，不在本任务书内改动。

### 5.8 token 预算上下文（F-8）

**问题**：当前 `MAX_MESSAGES = 20` 按条数截断，20 条长文可爆上下文窗口。

`src/main/modules/chat/service.ts`：
- 新增 `estimateTokens(text: string): number`——轻量估算：中文/全角字符按 1 token、ASCII 按 `Math.ceil(len / 3)`（**不引入 tiktoken 依赖**，估算即可）
- `run` 构造上下文改为 **token 预算**（默认 `CONTEXT_TOKEN_BUDGET = 6000`）：
  1. system prompt 先占位（计入预算）
  2. 从 `context.messages`（历史，新→旧）倒序累加，直到预算耗尽；超出部分丢弃（最旧优先丢弃）
  3. 若单条消息本身超过预算 → 强制截断该消息尾部，保证至少包含最新一条
- 删除 `MAX_MESSAGES` 常量；保留「最近 20 条」作为**兜底上限**（防极端小预算），`MAX_CONTEXT_MESSAGES = 40`
- 约束不变：情绪数据永不入上下文

| 重新生成 | 复用 `ai:chat:start`（前端把**末条用户消息**重发，需先删除原 assistant 回复） | 新 IPC `sessions:regenerate`（`{ sessionId }`）：删除该会话**最后一条 assistant 消息** → 返回最后一条 user 消息内容 → 前端直接调 `ai.start` 重发；无可重生成（无 user 消息）→ `VALIDATION_ERROR` |
| 删除单条 | 新 IPC `messages:remove`（`{ id, sessionId }`，确认字段沿用 `confirmationSchema`） | 仅允许删除**最后一条**消息（防破坏上下文序列）；删除后该轮上下文自然回退 |
| 清空会话 | 新 IPC `sessions:clear`（`{ id, confirmation }`，确认短语「清空」） | 删除会话内**全部消息**但保留会话；清空前停止活动流 |

- `ai_message` 消息 DTO 在 `session:messages` 返回 `id`（已返回），UI 操作依赖 id
- 删除/清空后前端刷新消息列表

### 5.10 流式中断自动重试（F-10）

`src/main/modules/chat/service.ts`：
- 断流定义：`chatStream` 抛错 **且** `active.controller.signal.aborted === false`（非用户中止）
- 行为：自动重试 **1 次**——重新构造 provider、重新 `chatStream`（请求体相同）；重试前把已收到的 `active.text`/`active.reasoning` 清空（LLM 无状态，无法续接，整轮重发）
- 重试仍失败 → 走既有错误处理（回滚用户消息 + 错误事件 + UI 显示重试按钮 F-15）
- 自动重试**不通知 UI**（静默），仅影响耗时；用户侧表现为响应变慢
- 用户停止（abort）**不重试**，直接走中止路径

### 5.11 全局并发限制（F-11）

`src/main/modules/chat/service.ts`：
- 类内维护 `private running = 0`；`start` 时 `if (running >= 2) throw { code: "CONFLICT", message: "已有 2 个会话正在生成，请等待完成" }`；`run` 的 `finally` 中 `running -= 1`
- 复用既有 `CONFLICT` 错误码（前端展示 message），不新增错误码
- 不做排队队列（复杂度不值得）：并发满直接拒绝，用户稍后重试

### 5.12 token 用量展示 + 模型标识（F-12）

- `src/main/infrastructure/llm/types.ts`：`ChatResult.usage` 扩展 `reasoningTokens?: number`
- `openai-compatible.ts` 解析：OpenAI 系 `completion_tokens_details.reasoning_tokens`；DeepSeek 等直接 `usage.reasoning_tokens`；两者兼容取非空值
- `chat/service.ts`：`ai:chat:done` payload 增加 `usage?: { promptTokens, completionTokens, reasoningTokens? }`
- UI：气泡角标（右下小字）显示「↑in ↓out」token 数（含思考 token 时显示「思考 N」）；气泡旁显示模型名（`model`）；无 usage 时省略
- 不落库（用量为运行时信息）

### 5.13 长会话性能（F-13）

`AssistantPage.vue` + `src/renderer/shared/markdown.ts`：
- **虚拟滚动**：消息数 > 100 条时启用虚拟滚动（优先用 Element Plus 内置 `el-virtual-list`；或手写定高/不定高简化实现）。注意与「加载更早消息」按钮协同：顶部加载时保留滚动位置
- **渲染缓存**：`renderMarkdown` 加 memoize（以 content 为 key 的 LRU，容量 200）——历史消息不重复解析；流式中的消息不缓存（每次渲染前检查 key 变化）
- 完成后切 Markdown 的整条重渲染只发生一次（配合缓存）

### 5.15 失败重试按钮（F-15）

`AssistantPage.vue`：
