# PRD: 人生系统 v1

**Status**: Draft  
**Product Owner**: Alex  
**Target**: 单用户桌面端 Electron 应用  
**定位**: 离线优先的个人目标、行动、知识与自我回顾系统

## 1. Problem Statement

用户的目标、待办、习惯、知识、个人记录和情绪数据分散在多个工具中，导致：

- 目标无法落到具体行动，行动完成后也无法回溯目标进展。
- 知识只能收藏，难以稳定导入、检索、引用和问答。
- 日记、灵感、决策和项目经验无法形成长期可回看的个人资产。
- 计划、执行、复盘之间断裂，管理工具本身成为负担。

**核心用户**: 个人使用者，主要面向有目标管理、知识积累和自我复盘需求的知识工作者。

**核心产品假设**:

> 如果把“目标 → 项目 → 待办”与“记录 → 回顾”放在同一个离线优先系统中，用户就能减少工具切换，并更持续地推进目标、沉淀知识和理解自己。

## 2. Goals & Success Metrics

| 目标 | 指标 | 初始基线 | v1 目标 |
|---|---|---:|---:|
| 保持持续使用 | 每周完成核心动作的天数 | TBD | ≥ 4 天 |
| 降低计划失焦 | 每周至少一次目标/待办回顾比例 | TBD | ≥ 60% |
| 提升行动完成 | 待办完成率 | TBD | 较基线提升 20% |
| 提升目标可见性 | 有实际数据或里程碑更新的目标比例 | TBD | ≥ 70% |
| 提升知识可用性 | 用户通过搜索/RAG 找到目标内容的成功率 | TBD | ≥ 70% |
| 支持自我觉察 | 情绪记录后的自评帮助度 | TBD | ≥ 3.5/5 |
| 降低焦虑 | 负面情绪强度中位数趋势（自评，非因果） | TBD | 呈下降趋势 |

不追求打开次数、使用时长、完成数量排名或游戏化。

## 3. Non-Goals

v1 不包含：

- 多端同步、移动端、多人协作。
- 外部通知渠道、社交分享。
- 四象限、优先级体系。
- 人生愿景、领域实体、个人 OKR。
- 阅读进度和书单管理。
- 情绪记录与目标、待办、知识的自动关联。
- AI 自动执行或自动修改目标、计划、待办。
- 外部平台 API 自动同步。

## 4. Core Model

### 目标线：想达成什么

目标支持三种度量类型：

1. **数值型**：起点值、目标值、数据点、趋势。
2. **里程碑型**：子项勾选，进度为已完成数/总数。
3. **状态型**：进行中、已完成、已放弃，无进度条。

进度只能由真实数据或真实完成驱动，不根据待办数量推算结果。

### 行动线：准备做什么

- **项目**：有明确起止时间和成果的行动容器，可挂目标，也可独立存在。
- **待办**：单次行动，最多关联一个目标和一个生活项目。
- **习惯**：独立实体，拥有打卡历史和连续天数，不与待办合并。

### 回顾线：发生过什么

- 时间线记录：日记、灵感、决策记录、阅读记录（周复盘独立走固定三问流程）。
- 记录可通过 `entity_link` 关联目标、项目、待办、知识文档和开发项目。
- 记录可一键升格为知识库文档。

### 知识线：长期可复用什么

- 收藏箱是暂存区。
- 知识库是经过处理后的长期内容。
- RAG 只默认检索知识库；只有用户明确要求时，才读取其他模块数据。

## 5. Functional Scope & Priority

### P0：必须跑通的核心闭环

| 功能 | 范围 |
|---|---|
| 目标管理 | 三种目标类型、数据点、里程碑、状态流转 |
| 生活项目 | CRUD、起止时间、可选关联目标 |
| 待办 | CRUD、截止时间、完成、按目标/项目筛选 |
| 目标行动区 | 查看目标下关联待办和项目 |
| 习惯 | 创建、每日打卡、连续天数、历史记录；与待办并列作为执行层核心功能 |
| Dashboard | 主区为今日行动（待办 + 习惯打卡）；次区为目标进展摘要、近期目标和到期提醒 |
| 周期提醒 | 目标到期、习惯打卡、数据录入，站内可配置 |
| 数据安全 | MySQL + Milvus 一键备份，JSON/Markdown 导出 |
| 基础搜索 | 标题、正文、标签、类型检索 |

### P1：形成“回顾与知识”价值

| 功能 | 范围 |
|---|---|
| 收藏箱 | 链接、片段、备注；剪藏入库、仅保留、丢弃 |
| 知识库 | 手写、Markdown、TXT、HTML、PDF、Word 导入 |
| 文档管理 | 标签、来源、编辑、导出 PDF/Markdown/TXT |
| RAG | 分块、本地 embedding、语义检索、带引用问答 |
| Prompt 模板 | `usage_tags`、复制、搜索 |
| 时间线沉淀 | 日记、灵感、决策、阅读记录 |
| 升格机制 | 时间线记录转知识文档，保留原记录 |
| 周复盘 | 固定三问模板，关联本周实体 |
| 心理健康 | 情绪五要素、细粒度词库、强度图表、AI 周报；保留在 v1，安排在 AI 阶段开发 |

### P2：v1 后半段交付（范围保留，工程顺序靠后）

| 功能 | 范围 |
|---|---|
| 开发项目 | 想法收集、价值/可行性评估、一键立项 |
| 开发看板 | 自定义状态流、拖动切换、阶段进度 |
| 洞察页 | 目标趋势、逾期模式、复盘摘要 |
| 日检视/月度回顾/季度规划 | 周期性回顾流程 |
| 日历与时间预算 | 待办日期、时间块、时长预算 |

## 6. 关键用户流程

### 目标推进

`创建目标 → 选择度量类型 → 可选创建项目 → 添加待办/里程碑 → 执行动作 → 更新真实数据 → 查看进展`

### 知识沉淀

`收藏链接或导入文件 → 收藏箱处理 → 剪藏入库 → 分块与向量化 → 搜索/RAG 问答 → 引用原文`

### 个人回顾

`创建灵感/决策/阅读记录 → 时间线查看 → 关联实体 → 周复盘 → 必要时升格为知识文档`

### 情绪觉察

`记录情绪 → 查看分布与趋势 → 生成周报 → 阅读建议`

AI 只提供候选分析和建议，不自动修改用户数据。

## 7. 技术与依赖

- Electron + Vue 3 + TypeScript。
- MySQL 作为业务唯一事实源，Milvus 作为可重建的知识向量索引。
- 本地 embedding 模型。
- LLM API 用于 RAG 问答和情绪周报。
- PDF/Word/HTML/Markdown/TXT 解析依赖 JS 生态库。
- 当 MySQL 与 Milvus 部署在本机时，所有核心记录和检索功能必须在无公网情况下可用；若服务部署在远端，核心功能依赖到服务的网络连接。AI 功能断网时降级为不可用并明确提示。
- PDF/Word/Markdown/TXT/HTML 均属于首版知识库和 RAG 导入范围。工程上可先完成 Markdown/TXT/HTML，再紧随完成 PDF/Word，但不得从首版范围中移除。

## 8. 主要风险

| 风险 | 等级 | 缓解措施 |
|---|---|---|
| 范围过大，长期无法发布 | 高 | 按 P0/P1/P2 分阶段交付，每阶段单独验收 |
| 录入复杂导致放弃 | 高 | 每页一个主操作，高级字段折叠，默认模板 |
| RAG 导入质量不稳定 | 高 | 先完成 Markdown/TXT/HTML 解析链路，再紧随完成 PDF/Word；五种格式均须在首版交付 |
| 目标进度模型被误解 | 中 | 明确区分“结果进度”和“行动完成” |
| AI 建议不可靠 | 中 | 带引用、标注不确定性，不做诊断或自动执行 |
| 数据备份恢复失败 | 高 | v1 早期完成一键备份/恢复测试，并提供导出校验 |

## 9. 发布建议

不建议把上述全部内容称为一个 MVP。建议拆为三个发布门：

1. **MVP-1：目标行动闭环**：P0 全部功能，验证用户是否持续使用目标、待办、习惯和回顾。
2. **MVP-2：知识与沉淀闭环**：收藏箱、知识库、PDF/Word/Markdown/TXT/HTML 导入、时间线、升格和 RAG。
3. **MVP-3：v1 其余范围**：心理健康、开发项目、洞察页、周期节奏和日历。心理健康属于 v1，安排在 RAG 之后开发，以复用 LLM 抽象层，并非后置或取消。

MVP-1、MVP-2、MVP-3 是工程发布门，不代表删除已确认的 v1 范围。每个发布门都应先完成验收和稳定性验证，再进入下一阶段。

## 10. 已确认的产品决策

- **习惯属于 P0**：习惯页、打卡和连续天数与待办并列构成执行层，不能后置。
- **RAG 属于首版核心**：首版必须覆盖 PDF、Word、Markdown、TXT、HTML 导入及带引用问答；允许调整开发顺序，不允许砍掉范围。
- **心理健康属于首版范围**：情绪五要素、词库、统计图表和 AI 周报保留，工程上安排在 RAG 之后开发。
- **Dashboard 首屏主操作**：主区为“今日行动”（待办 + 习惯打卡），次区为目标进展摘要卡片。
- **备份恢复范围**：第一版只做一键备份和一键恢复（MySQL dump + Milvus 快照/JSON/Markdown），不做版本历史、冲突检测或协作合并；本机部署服务不可用时不能承诺离线恢复。
